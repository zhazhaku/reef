# 产品方案矩阵：reef + ESP32-S3 ePaper 创新应用

> **报告人**: product-designer  
> **日期**: 2026-06-15  
> **基于**: 硬件研究报告 / 固件研究报告 / reef-ESP32-S3 架构设计  
> **目标**: 从 5 个差异化方向中选定 1-2 个深入开发

---

## 方向 1：墙上的语音便签

### 目标用户场景
**核心用户**: 有孩子的双职工家庭（3-5 口之家），每天通勤、接送、补习班，成员时间表交错，靠微信群/纸条传递信息。

**场景 1** — 妈妈早上 7:30 出门前对着便签说："提醒爸爸下午 4 点接小宝，别忘了带跆拳道服。" 设备收音→ reef LLM 提炼为一条结构化便签→ ePaper 刷新显示 "📋 4:00PM 接小宝 | 带跆拳道服 | —妈妈"。爸爸早上 9 点起床瞥一眼屏幕，不再需要翻微信群聊记录。

**场景 2** — 孩子放学回家按一下按键，便签自动刷新显示当天 reef server 推过来的家庭公告（明天家长会 / 冰箱里剩菜请吃掉 / 快递已到驿站）。不用打开手机，不用登录任何 APP。

### 核心创新点
1. **"说→留→看"闭环 vs 微信群碎碎念**: 微信群消息会被淹没、被误解、被忽略。语音便签通过 reef LLM 把口水话提炼为结构化卡片（who/what/when），持久显示在物理硬件上——注意力成本为零。
2. **物理存在感的信任优势**: 手机推送可以被划掉、被静音、被忽略。墙上便签的物理显示是一种温和但难以忽视的家庭契约——"白纸黑字写在这儿了"。

### 三句话用户体验流
1. 用户按住按键说话："明天记得带垃圾出门，周四是回收日" → LED 亮蓝灯表示收音中
2. 松开按键，xiaozhi-ai 本地 ASR 转文字 → reef server LLM 提炼为 "🚮 周四回收日 | 带垃圾出门" → ePaper 局刷 0.5 秒更新
3. 其他家庭成员路过便签，瞥一眼即知。按一下按键可语音回复 "知道了" → reef 记录确认状态，ePaper 显示 "✅ 爸爸已确认"

### reef 端如何赋能
- **LLM 提炼与翻译**: server 端 LLM 把口语转结构化卡片（意图识别+实体抽取+优先级排序），支持中英日多语言家庭成员混用
- **跨设备同步**: 家中多个便签节点组成 swarm，server 协调消息广播；办公室和家里各一块，"对家里的便签说今晚加班" → server 推送至对应设备
- **外部 API 集成**: reef server 接入日历 API / 快递查询 API，混合显示家庭公告+外部事件（"📦 顺丰快递已签收 | 京东预计明天到"）

### xiaozhi 在其中的角色
语音入口 + 轻量对话。xiaozhi-ai 负责按键触发的 ASR（语音转文字）和确认性 TTS（"好的，已记录"）。reef-client 在后台保持 WS 连接，收到 `task_dispatch`（display_text）时接管 ePaper 刷新。两者通过模式切换共存：**语音交互时 xiaozhi 持有 ePaper，reef 刷新时 reef 持有 ePaper**。

### 可行性自评
| 维度 | 评估 |
|------|------|
| **硬件契合度** | ⭐⭐⭐⭐⭐ 完美。电子纸盯着看是核心价值（零功耗常亮），200×200 显示 3-5 条中文卡片绰绰有余，刷新频率低（日均 10-20 次） |
| **续航天数** | 日均 15 次 ePaper 全刷 + 5 分钟 Wi-Fi 活跃 + BLE 广播：~80mA 平均，1000mAh → **~12 小时活跃 / ~4-7 天续航**（深度睡眠优化后可达 2-3 周） |
| **技术风险** | 低。核心链路（ASR→LLM→ePaper 刷新）已被各组件单独验证；风险点仅在于 reef LLM 提炼 prompt 的准确率调优 |
| **MVP 工作量** | 8-12 人天：reef-client 移植（3d）+ LLM 提炼 prompt（2d）+ 便签 UI（2d）+ 按键/语音流程（3d）+ 联调（1-2d） |

## 方向 2：健康哨兵

### 目标用户场景
**核心用户**: 独居老人（70+ 岁，有慢性病需每日服药）及其异地子女。

**场景 1** — 老人每天早上 8 点看到 ePaper 显示 "💊 降压药 1片 | 降糖药 1片 | 请按按钮确认已吃"。老人吃完药按一下按键，屏幕从红色 "⏳ 待服药" 变为绿色 "✅ 8:12 已服药"。如果上午 10 点仍未确认，设备发出温和的 TTS 语音提醒 "李阿姨，该吃药了"。如果中午 12 点仍无确认，reef server 通过飞书/短信通知远在外地的子女。

**场景 2** — 子女在 reef server 面板看到一周服药记录："周一 8:12, 周二 8:05, 周三 **未服药**"。子女通过 reef 下发语音消息："妈，昨天降压药忘吃了，今天记得啊"。设备 ePaper 显示 "📞 儿子留言: 记得吃降压药" + TTS 播放。

### 核心创新点
1. **"不打扰的监视" vs 摄像头监控**: 摄像头侵犯隐私，老人抵触。健康哨兵通过一个无害的"吃药看板"形态自然地获得了老人的日常活动信号（按键交互），子女只收到异常告警而非全天监控——**隐私感和安全感兼得**。
2. **自适应提醒策略**: 市面上的药盒只会定时响。健康哨兵通过 reef LLM 学习老人的响应模式（总是 8:05-8:15 间确认 → 正常；今天 9:30 还没确认 → 异常），差异化升级提醒和通知。

### 三句话用户体验流
1. ePaper 始终显示当日服药清单（永不休眠，老人不用学"解锁手机"这个操作）
2. 老人吃完药按按键，屏幕更新为 "✅ 已服" → reef server 记录时间戳
3. 如超时未确认：本地 TTS "请服药" → 再次超时 → reef server 通知子女 → 子女可远程语音留言，ePaper 显示留言内容

### reef 端如何赋能
- **异常检测**: reef server 分析长期服药数据，检测模式偏离（连续两天晚服 → LLM 判断是否需要调整提醒策略）
- **远程关怀通道**: 子女通过 reef server→ client 下发 task_dispatch (display_text + tts)，确保老人的设备用最简单的方式接收消息（不需要操作手机 APP）
- **多设备协同**: 如果老人家里有多个 reef 设备（厨房一个、卧室一个），server 自动选择最近交互过的设备推送提醒

### xiaozhi 在其中的角色
警告级 TTS 播报（服药提醒）+ 紧急语音留言。正常状态下 xiaozhi 休眠（省电），仅在需要语音交互时唤醒。reef-client 始终维持 WS 长连接，驱动 ePaper 显示。**xiaozhi 在此场景下退居辅助角色**。

### 可行性自评
| 维度 | 评估 |
|------|------|
| **硬件契合度** | ⭐⭐⭐⭐ 良好。ePaper 常亮特性是老年产品刚需（无需解锁/唤醒屏幕）。按键足够大。缺少 LED 指示灯颜色区分（如需红绿提示需外接） |
| **续航天数** | 日均 5 次 ePaper 刷新 + 几乎不 Wi-Fi（只在异常时联网播报 TTS）→ **1-2 月续航** |
| **技术风险** | 中高。核心风险不在技术实现，而在**用户体验打磨**：字体必须极大（老人视力）、按键触感必须清晰、语音播报音量必须够大。此外，GPIO 紧张——如需外接 LED 需要解决 |
| **MVP 工作量** | 15-20 人天：reef-client 移植（3d）+ 服药管理逻辑（3d）+ 大字体 UI + 红色反色（2d）+ 按键流程（2d）+ reef server 告警通知（3d）+ 子女通知通道（2d）+ 用户测试（5d） |

## 方向 3：会议门神

### 目标用户场景
**核心用户**: 共享办公空间运营方 / 20-100 人公司行政团队。

**场景 1** — 会议室门口贴着一块 ePaper 牌："🟢 空闲至 14:00 | 下个会议: 产品评审会 14:00-15:00"。路过的人瞥一眼就知道能不能用。有人想临时约个会，按下按键说："三点到四点能用吗？"→ reef LLM 查询日历→ TTS 回复 "三点到四点空闲，已帮你预约"→ 屏幕更新。

**场景 2** — 行政团队在 reef server 看板看到所有会议室的实时状态和占用率统计。发现 3 号会议室连续 3 天下午空闲 → reef 建议是否释放或重新分配。

### 核心创新点
1. **免布线 + 免维护 vs 传统电子门牌**: 传统会议室屏需要 PoE 网线或电源布线，安装成本 500-2000 元/个。会议门神用电池+ePaper+Wi-Fi，双面胶一贴即用，成本控制在 150-200 元/个——**大规模部署的门槛降到零**。
2. **自然语言预约 vs 掏出手机打开日历 APP**: "三点能用吗" 是最自然的交互，不需打开任何 APP、不需要学任何操作。

### 三句话用户体验流
1. 有人走到会议室门口，ePaper 黑底白字显示 "🔴 使用中 | 至 14:30" → 直接走开
2. 有人按按键说话："两点半之后有空吗？" → LED 亮蓝灯录音 → TTS "两点半之后全天可用" → 屏幕局刷显示新状态
3. 会议开始时有人按按键说 "开始会议：季度复盘" → reef 记录占用 → 屏幕更新为 "🔴 季度复盘 | 开始 14:00"

### reef 端如何赋能
- **日历 API 集成**: reef server 接入 Google Calendar / 飞书日历，实时同步会议室预定状态
- **占用分析**: reef LLM 分析历史占用数据，发现异常（如某会议室总是被预订但实际空置 → 建议管理员调查）
- **跨楼层 swarm**: 一楼会议门神和二楼会议门神同属一个 reef swarm，server 可跨楼层推荐空闲会议室（"3 楼 302 现在空着"）

### xiaozhi 在其中的角色
纯语音交互入口。会议室场景不涉及持续音频流，xiaozhi 仅在按钮触发时执行 ASR→TTS。**xiaozhi 在此场景中功能完整保留，但使用频次很低**。

### 可行性自评
| 维度 | 评估 |
|------|------|
| **硬件契合度** | ⭐⭐⭐⭐⭐ 极佳。会议室场景天然适合 ePaper（静态信息常亮），电池供电免除布线，200×200 分辨率对 "使用中/空闲+下个会议" 的信息密度完美匹配 |
| **续航天数** | 日均 20-30 次 ePaper 刷新 + 常连 Wi-Fi → **3-5 天**（如启用深度睡眠 + 定时唤醒刷日历 → **2-3 周**） |
| **技术风险** | 低。日历 API 对接成熟，核心链路短。风险点：深度睡眠模式下 Wi-Fi 唤醒后的重连时间（2-5 秒）可能导致按键响应慢 |
| **MVP 工作量** | 6-8 人天：reef-client 移植（3d）+ 日历 API 对接（1d）+ UI（1d）+ 语音流程（2d）+ 联调（1d） |

## 方向 4：家庭看板蜂群

### 目标用户场景
**核心用户**: 智能家居爱好者 / 极客家庭（已有一定的智能设备，追求 "数据在墙上" 而不是 "数据在手机里"）。

**场景 1** — 厨房 ePaper 显示 "🍳 今日菜谱: 番茄炒蛋 | 冰箱里食材可做 3 道菜 | 牛奶明天过期"。客厅 ePaper 显示 "🌡️ 室内 24°C 湿度 55% | 📺 今晚 8 点《权力的游戏》新集"（通过 reef 接入家庭传感器和流媒体 API）。卧室 ePaper 显示 "😴 昨晚睡眠评分 78 | 建议今晚 11 点前入睡"。

**场景 2** — 用户出门前对客厅看板说 "我今天穿什么？"→ reef LLM 综合天气 API（15°C 有雨）+ 衣柜传感器（如果有）→ TTS "建议穿风衣带伞"→ ePaper 显示穿搭建议。

### 核心创新点
1. **"去中心化家庭数据墙" vs 手机中心化**: 智能家居现状是所有数据汇聚到手机 APP，但手机是你最不想在家的时刻盯着的东西。家庭看板把数据散落到家中每个物理空间——厨房看菜谱、客厅看天气、卧室看睡眠——"路过即知"。
2. **reef swarm 多节点协同**: 这是 5 个方案中唯一利用 reef swarm 多 client 协调的方案。server 根据数据来源自动路由到最合适的设备——厨房菜谱不会出现在卧室看板上。

### 三句话用户体验流
1. 厨房看板每天早晨自动更新 "菜谱推荐"（reef 读取冰箱库存 + 菜谱 API + LLM 生成）→ ePaper 局刷
2. 用户路过客厅看板自然瞥见天气和室内温湿度 → 不需要任何操作
3. 对任意看板说话："帮我查快递"→ reef server 查询 → TTS + ePaper 显示结果

### reef 端如何赋能
- **多节点路由**: reef server 维护所有家庭 client 的 role/skills，"菜谱" task 自动 dispatch 到 role="kitchen-display" 的节点，"天气" 到 role="living-room"
- **数据聚合与 LLM 生成**: server 聚合传感器数据→ LLM 生成自然语言摘要（"今天湿度偏高，建议开窗通风" 而不是原始数值）
- **外部 API 编排**: reef server 作为家庭数据中枢，接入天气/快递/日历/流媒体/菜谱等外部 API，LLM 统一编排分发

### xiaozhi 在其中的角色
语音交互入口，但**不再是单一设备**——任意一块看板都可以触发语音对话（通过唤醒词或按键）。xiaozhi-ai 固件在所有节点上运行，但实际对话由最近触发的节点处理。**reef server 负责协调多节点冲突**（两人同时对不同看板说话时）。

### 可行性自评
| 维度 | 评估 |
|------|------|
| **硬件契合度** | ⭐⭐⭐⭐⭐ 极佳。多块 ePaper 散落家中是最自然的物理形态，每块成本可控 (~150 元, 远低于 iPad/智能屏) |
| **续航天数** | 单节点日均 10-15 次刷新 + 常连 Wi-Fi → **3-7 天**；深度睡眠优化后 → **1-2 周** |
| **技术风险** | 中高。多节点协同涉及 server 端路由逻辑（哪个 task 发给哪个节点），以及多节点同时语音交互的冲突处理 |
| **MVP 工作量** | 20-25 人天：reef-client 移植+role 路由（3d）+ 数据聚合+LLM 生成（5d）+ 多块 UI 适配（3d）+ 外部 API 对接（3d）+ 多节点协调逻辑（5d）+ 联调测试（3d）+ 硬件复制（3d） |

## 方向 5：专注番茄钟

### 目标用户场景
**核心用户**: 知识工作者（程序员/设计师/写作者）、考研学生——需要深度专注又容易被手机分心的人群。

**场景 1** — 用户对番茄钟说："开始一个 25 分钟的番茄钟，任务是写周报。" ePaper 显示 "🍅 写周报 | ████░░░░░░ 10:24 剩余" 并开始倒计时。**关键：手机自动进入勿扰模式**（通过 reef server 调用手机端 API 或 Shortcuts）。

**场景 2** — 番茄钟结束，ePaper 显示 "✅ 完成！休息 5 分钟" + reef LLM 生成的一句鼓励语 "别抬头，还有 3 个番茄你就写完这篇论文了"。用户可以按键查看今日统计 "今天已完成 🍅🍅🍅🍅 4/8"。

### 核心创新点
1. **"反手机"专注伴侣**: 番茄钟 APP 最大的悖论是——你需要在手机上打开它，但手机就是分心的源头。实体番茄钟没有推送、没有通知、没有小红点。ePaper 的慢刷新特性反而是优势——你无法在上面刷短视频。
2. **reef LLM 专注教练**: 不是简单的倒计时器。reef LLM 分析你的番茄完成模式（几点效率最高 / 哪些任务总超时 / 连续专注几天后需要休息）→ 给出个性化建议。

### 三句话用户体验流
1. 用户按按键说 "开始写代码 45 分钟" → LED 蓝灯 → ePaper 显示大号倒计时数字
2. 倒计时结束 → ePaper 更新 "✅ 休息！" + 一句鼓励 → reef 记录完成（可选：播放一段舒缓 TTS）
3. 一天结束 → 用户按键查看统计 → ePaper 显示 "🍅x8 今日 6h 专注 | 本周最佳！" → reef server 生成周报

### reef 端如何赋能
- **专注分析与建议**: reef LLM 分析多日数据，发现用户下午 2-4 点效率最高 → 建议 "明天把最难的任务安排在下午"
- **社交激励**: reef swarm 中多个番茄钟节点之间可以形成小组（如团队全员番茄竞赛），server 协调排行榜显示
- **环境联动**: reef server 可联动智能灯（番茄开始时调暖光）或电脑状态（调用 API 关闭社交媒体网站）

### xiaozhi 在其中的角色
极简语音输入（设置任务名和时长）+ 番茄结束时的 TTS 提醒。**xiaozhi 在正常番茄运行期间完全静默**，仅 reef-client 驱动 ePaper 倒计时。

### 可行性自评
| 维度 | 评估 |
|------|------|
| **硬件契合度** | ⭐⭐⭐⭐ 良好。ePaper 慢刷新恰好适配倒计时（每分钟刷新一次即可），低功耗适合全天使用。但 1.54 寸对"大号倒计时数字"来说略小 |
| **续航天数** | 日均 60-120 次刷新（每分钟约 1 次）+ Wi-Fi 常连 → **1-2 天**。这是最大弱点——频繁刷新严重消耗电池 |
| **技术风险** | 中。局刷倒计时需要稳定（不能有残影积累），需要周期性全刷清理。续航是核心问题——可能需要用户在桌面放置时 USB 供电 |

## 最终推荐：方向 1 — 墙上的语音便签 🥇

### 推荐理由（硬件契合度 + 市场新颖度 + 落地难度三维度）

**1. 硬件契合度 ⭐⭐⭐⭐⭐** — 完美匹配。

电子纸的核心优势（零功耗常亮 / 静态信息展示）在便签场景中被充分利用。200×200 分辨率显示 3-5 条结构化卡片（emoji 图标 + 一句话 + 时间戳）完全够用。每天仅需 15 次刷新，电池轻松撑一周。按键和麦克风是唯一的交互方式——不需要触摸屏、不需要复杂 UI。

**2. 市场新颖度 ⭐⭐⭐⭐⭐** — 市面上没有直接竞品。

- 不是智能音箱（小爱/天猫精灵做不到"留一张便签在墙上"）
- 不是电子相框（Google Nest Hub 需要插电、需要盯着看、不能贴墙上）
- 不是小白板/冰箱贴（物理便签不会自动提炼、不能远程留言、不能多设备同步）

"用语音说话→设备自动提炼→电子纸持久显示" 这个闭环目前没有任何消费级产品实现。它填补了"家庭异步沟通"这个被微信群统治但一直体验糟糕的场景。

**3. 落地难度低** — MVP 只需 8-12 人天。

核心链路（ASR→LLM 提炼→ePaper 刷新）中的每个组件都已被单独验证：
- ASR: xiaozhi-ai 已有 (`esp-sr` 离线唤醒词 + 云端 ASR)
- LLM 提炼: reef server 端 LLM 只需一条 system prompt
- ePaper 刷新: Waveshare SDK 例程已验证
- reef 协议: connector.go 已在 Go 端跑通

唯一的"新"工作是把这些组件串起来 + 调优 LLM 提炼准确率。不需要硬件改造、不需要多设备协调、不需要外部 API 对接。

**4. 可扩展性强** — 从 MVP 到产品化的路径清晰。

- V1: 单设备 + 本地便签（MVP, 2 周）
- V2: 多设备同步 + 家庭成员确认（1 月）
- V3: 接入外部日历/快递 API（1.5 月）
- V4: reef swarm 跨设备同步 + 自然语言查询历史便签（2 月）

每一步都增加有意义的用户价值，且每一步都不需要推翻前一版的架构。
